Cenário 1 — DiscountService 55% mutation score

Gap #1 — Ramo "cliente comum" sem asserção de valor exato

Classe: DiscountService · Método: calculateDiscountRate · Linhas: 65, 75, 76
  • L65 — RemoveConditionalMutator_EQUAL_IF (condição if (vipCustomer) forçada para sempre true)
  • L75 — ConditionalsBoundaryMutator (>= → > em purchaseAmount >= VIP_THRESHOLD)
  • L75 — RemoveConditionalMutator_ORDER_IF / ORDER_ELSE (condição forçada para true/false)
  • L76 — PrimitiveReturnsMutator (return REGULAR_HIGH_DISCOUNT; trocado por return 0.0d;)

Por que sobrevive: os testes atuais para cliente comum (regularCustomerWithHighPurchaseHasSomeDiscount e regularCustomerWithLowPurchaseDoesNotThrow) usam assertTrue(result <= 1000.0) e assertDoesNotThrow(...). Nenhuma asserção verifica o valor exato do desconto (5% ou 0%), então qualquer mutação nesse ramo continua "passando" nos testes.

Gap #2 — Boundary de valor negativo/zero não testado com precisão

Classe: DiscountService · Métodos: calculateFinalPrice, calculateDiscountRate · Linhas: 45, 61
  • L45 — ConditionalsBoundaryMutator (< → <= em purchaseAmount < 0, dentro de calculateFinalPrice)
  • L45 — RemoveConditionalMutator_ORDER_ELSE (condição forçada para false)
  • L61 — mesmos dois mutantes, dentro de calculateDiscountRate

Por que sobrevive: o único teste de validação usa purchaseAmount = -1.0. Nenhum teste chama o método com purchaseAmount = 0.0 exatamente — o valor limite da regra "negativo lança exceção". Se o operador virar <=, 0.0 passaria a lançar exceção indevidamente, e nenhum teste perceberia.

Cenário 3 — PricingService 97% mutation score

Gap #8 — Piso mínimo de preço (MIN_PRICE_FACTOR) parece inalcançável com as regras atuais (achado de design, não apenas de teste)

Classe: PricingService · Método: calculatePrice · Linha: 83
  • L83 — MathMutator (multiplicação trocada por divisão em product.basePrice() * MIN_PRICE_FACTOR * quantity)
Este mutante é diferente dos demais: não é apenas "faltou um teste". A análise da fórmula sugere que, com as regras de negócio atuais, o piso mínimo nunca é de fato selecionado por Math.max.

Por que sobrevive (análise matemática):

  • Desconto máximo por quantidade é 15% (fator final 0.85).
  • Piso mínimo exige fator ≥ 0.8 do basePrice.
  • STANDARD: fator final mínimo = 0.85 → sempre acima do piso (0.8).
  • PREMIUM (1.5x): fator final mínimo = 1.5 × 0.85 = 1.275 → muito acima do piso.
  • SEASONAL normal (1.2x) e baixo estoque (2.0x): fatores ainda maiores → nunca atingem o piso.

Ou seja: não existe combinação válida de categoria + quantidade, dadas as regras descritas, em que minimumTotal > totalWithDiscount. Qualquer teste que tentarmos escrever para "forçar" o piso a ser escolhido vai falhar — porque o próprio código de produção nunca cai nesse caminho. Esse tipo de mutante costuma ser chamado de "mutante equivalente" (equivalent mutant): sobrevive porque a mutação não tem efeito observável no comportamento real do sistema.

Sugestões (nenhuma aplicada ao projeto)
  1. Confirmar com o time de negócio se o piso de 80% deveria ser alcançável com as faixas de desconto atuais (ex.: se um desconto futuro de 25%+ for planejado, o piso já está pronto — apenas não é exercitado hoje).
  2. Se o piso é intencionalmente "defensivo" (proteção para regras futuras), documentar isso no Javadoc do método e marcar o mutante como aceito no relatório (não vale a pena perseguir 100% de mutation score às custas de testes artificiais).
  3. Se possível reduzir o escopo do teste, um teste unitário isolado da fórmula (chamando calculatePrice com um basePrice hipotético e validando a invariante result >= basePrice * 0.8 * quantity para várias combinações via @ParameterizedTest) pelo menos documenta a invariante esperada, mesmo que não seja capaz de matar este mutante específico:
@ParameterizedTest
@DisplayName("Invariante: preço final nunca é menor que o piso, para qualquer tier de desconto")
@ValueSource(ints = {1, 4, 5, 9, 10, 19, 20, 50})
void priceNeverViolatesMinimumFloorInvariant(int quantity) {
    Product product = productWith(PricingRule.STANDARD, 100.0);
    when(productRepository.findById(PRODUCT_ID)).thenReturn(Optional.of(product));

    double result = pricingService.calculatePrice(PRODUCT_ID, quantity);
    double floor = 100.0 * 0.8 * quantity;

    assertTrue(result >= floor,
        // documenta a invariante, mas não mata o MathMutator na L83
        () -> "Preço " + result + " abaixo do piso " + floor);
}

Este é o único caso da POC em que a recomendação não é "escrever mais um teste", e sim revisitar a regra de negócio — um ótimo exemplo para a apresentação de como mutation testing revela não só gaps de teste, mas também código potencialmente morto/redundante.
